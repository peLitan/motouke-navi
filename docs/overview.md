# プロジェクト概要

使う前は法令と発注者の仕様書を自分で引いて確かめる必要があった元請けの確認を、使うと工事の条件を入れるだけで、読むべき原文の抜き書きつきの候補として見られます。確かめた数字: 架空の見本の書類3件に仕込んだ抜けと誤り11件のうち見つけたのは9件(2026-11-04 の採点。版 7ba4f4f、1fcb4ec の出力も同じ。9件のうち1件は部分一致で、見落としが2件)、和歌山県の仕様書の7つの節から作った31行のうち抜き書きが原文と合ったのは31行(「土木請負工事必携」令和7年11月版、check-rows。行の意味は人が確かめます)。

想定している場面: 下請けが中心だった小さな建設会社が、初めて自治体の工事を元請けで取った。元請けとしての決まりは建設業法などの法令と発注者の仕様書に分かれていて、社内に読める人がいない。手がかりになる国の作成例は、国の直轄工事のものだけ。この作品は、この想定の人物のために作りました(実在の人・会社・工事の話ではありません)。

作品名: Motouke Navi

テーマ: #2「本来、誰にでも届くべきものを。」 — 決まりが法令と仕様書に分かれていて読み解くのが難しい確認の手がかりを、初めて元請けをする小さな会社にも届けます

## 一言で
工事の条件を入れると、入札前の確認・施工体制台帳が要るか・受注後の段取りを、法令と国の仕様書の原文の抜き書きつきで出し、施工体制台帳と施工計画書の目次の抜けの候補も出す、ブラウザで開くだけの道具です。

## 誰の、どんな困りごとか
- 中小の建設会社で、入札・契約・書類を受け持つ担当者
- 「この金額なら特定建設業の許可が要るか」「施工体制台帳は要るか、写しは出すのか」「監理技術者か主任技術者か、専任か」を、そのたびに建設業法・施行令・入契法と国交省の資料を引いて確かめている
- 受注後は、共通仕様書のどの条で、いつ・何を・誰に出すのかを、着手から完成・引き渡しまで追う必要がある
- 台帳や施工計画書の抜けは、監督職員に言われて初めて気づくことがある

## このツールがすること
1. 入札前の確認と台帳の要否: 公共・民間、請負代金、下請けの総額、許可の種類などから、受注したら要るものを、根拠の条(法令名・条・項)と原文の抜き書きつきで出す
2. 受注後の段取り: 国の直轄の例として、着手まで・施工中・完成・引き渡しの段に分け、土木工事共通仕様書(案)令和8年3月の該当箇所と抜き書きつきで一覧にする
3. 施工体制台帳の点検: 貼った台帳(または国交省の作成例の様式の Excel)から、空の欄・技術者の種類・特定建設業・専任の要否の食い違いの候補を出す
4. 施工計画書の目次の点検: 共通仕様書 1-1-1-6 の記載事項と比べ、見当たらない項目を候補に出す
5. 書類の突き合わせ: 施工体系図や施工計画書の目次も貼ると、下請負人の一覧・技術者の氏名・発注者の名前を台帳と比べ、片方にしか無い下請負人や氏名の違いを候補に出す。同じ会社か決められないときと発注者の名前の違いは「判断できない」に回す
6. 文の置き換え: 外の AI に貼る前に、人名・会社名・住所・電話などを記号に置き換え、戻ってきた文を元に戻す。置き換えた後のファイルだけを Claude の API に送って点検する手元のプログラムと、Claude Code が生のファイルを読む操作の多くを止める設定も付ける(止めきれない操作があり、README に挙げる)。施設名の語尾の表は建設のほかに、例として医療の表がある(医療の書類での漏れの率は測っていない)
7. Claude Code のプラグイン: 生のファイルの読み込みを止める hook、置き換えた後の中身だけを返す MCP の道具、取得した条に照らして書類を点検する Skill、その候補を崩しにかかる反証の係をまとめた。プラグインのあり・なしを比べる評価のケース2件(仕込み10件)と採点のスクリプトも付けた(2026-11-03 に12回走らせた。見落としはあり・なしとも、ほぼ0で差が出ず、条番号と抜き書きが原文にある割合はありの方が高かったが、数え方がプラグインの側に有利で回数も各3回だけなので言い切らない。docs/評価.md の 5)。架空の書類1件で、プラグインを読み込ませて raw/ の Read が止まること・Skill と反証の係が呼ばれることを1回確かめた(置き換えの漏れ・置き換えすぎ、許可の確認が出ることも分かった。README の限界)

## 大事にしたこと
- 根拠を原文で示す: 規則表の行ごとに原文の抜き書きを持ち、機械で原文と照らす。合わない行は使わない。金額の境目もコードに書かず、抜き書きの文から読む
- 推測で埋めない: 入力から決められないことは「判断できない」と出す。結論は候補で、最後の判断は人がする
- 外へ出さない: 画面は外部と通信せず、入れた内容を保存しない。Claude に送るのは、置き換えた後の中身を利用者が確かめて「送る」と打ったときだけ

## Claude の使い方
作品の中の Claude Code の仕組みは、次のように使い分けました(どれも `plugin/` に入っています)。

| 仕組み | 役目 | なぜその仕組みか | 証拠(数字か記録の場所) |
|---|---|---|---|
| hook `guard-raw` | `raw/` の生のファイルを Read・Grep・Glob・Bash などで読む操作を止める | Claude の判断に任せず、道具が動く前に必ず通る所で止めるため | `tests/acceptance/claude-code.test.mjs`。架空の書類1件で Read が止まるのを1回確かめた(`docs/manual.md` の「読み込ませて確かめたこと」)。止めきれない操作がある |
| MCP `read_masked` | 置き換えた後の中身だけを Claude に返す | 止めるだけでは点検できないので、読む道を別に作り、置き換えを手元の道具の中で行うため | 初めて見る書類4件の漏れの率は、辞書に足さないと 37.8%、足すと 14.3%(2026-11-04 朝に commit 520ced6 で測った値で、そのあとの置き換えの直し(F31・F36)では測り直していない。`docs/mask-rate.md`)。漏れは0にならない |
| MCP `list_masked` | `raw/` の中のファイルの名前だけを返す | hook が一覧を見る操作も止めるので、名前を知る道が要るため。中身は返さない | 評価の「E1 あり 3」は名前が分からずに止まり、見落とし 5/5 だった(`docs/評価.md` の 5)。足した後、5 の評価は走らせていない。`list_masked` も許した公式の評価(`docs/評価.md` の 7)では、書類の元の名前8つのうち Claude に渡らなかったのは、あり 8・なし 0(各3回。2026-11-05 の走らせ直し)。名前は置き換えない |
| Skill `construction-check` | 取得した条に照らして書類を点検し、候補を条番号つきで出す | 手順と根拠にしてよい条と確かめのスクリプトを、1つにまとめて配るため | 条番号が原文にある割合は、あり 72.9%・なし 47.1%。抜き書きは、あり 79.3%・なし 18.8%(各6回。数え方はありの側に有利。`docs/評価.md` の 5)。条番号の確かめ `check-articles.mjs` は、画面なしの入口を版 156b15c で走らせた 2026-11-05 の回で単独で呼ばれ、33件のうち ある 33・無い 0・確かめられない 0 だった(`docs/manual.md`) |
| Skill `spec-to-rules` | 発注者の仕様書の文から段取りと記載項目の行を作り、原文と照らす | 文を読んで行にするのは Claude に任せ、抜き書きの位置は機械で確かめるため | 和歌山県の仕様書で 31 行のうち残す 31・外す 0・判断できない欄のある行 7。意味の正しさは人が確かめる。試したのは1件だけ(`docs/評価.md` の 6) |
| 反証の係 `refuter` | 候補を1件ずつ崩しにかかり、残る・崩れた・確かめられないで返す | 点検した側の見方を持ち込まない別の係にし、道具を `read_masked` だけにするため | 架空の書類1件で、10件のうち1件を「確かめられない」として外した(`docs/manual.md` の「読み込ませて確かめたこと」)。Skill の手順に書いた後の版 156b15c を画面なしの入口で走らせた回(2026-11-05)では、元の18件のうち 残る 15・崩れた 2・確かめられない 1 だった(`docs/manual.md` の「走らせた記録」) |
| 評価 `plugin/evals/` | プラグインのあり・なしを、同じ頼み方で比べる | 効いたかどうかを、作った側の感想でなく回数と数字で見るため | 2ケース × あり・なし × 3回 = 12回。見落としは、あり 5/30(すべて止まった1回)・なし 0/30。回数が少なく言い切らない(`docs/評価.md` の 5)。公式の評価 `claude plugin eval` では、書類の元の名前8つのうち Claude に渡らなかったのは、あり 8・なし 0(各3回。2026-11-05 に「丁山」の漏れを直した版で走らせ直した値)。直す前の 11/4 の版は、あり 7・なし 0 だった(`docs/評価.md` の 7) |

- 作り方: Claude Code が、1つずつの機能を短いセッションで作った。受け入れテストは人が承認したものを固定し、エージェントは直せない。原文の写しは reader、抜き書きの照合は checker、区切りの点検は critic という別の subagent に任せ、作る係の自己評価の甘さを補った(この3つは開始前に作った仕組みで、リポジトリの外にあり、審査の対象外。README の「Claude Code での作り方」)
- 作品の中: 置き換えた後の書類を Claude の API(`claude-opus-5-5`)に送り、点検の候補を「AI の候補」として、法令の決まりで判定した結果とは別の欄に出す

## 評価
- 受け入れテスト 21 ファイル・110 件が通る
- 規則表の抜き書き 99 件が原文にある(実在率 100%。2026-11-03)
- 架空の書類3件に別の係が仕込んだ抜けと誤り 11 件のうち、見つけた 9・見落とし 2・言い過ぎ 0(仕込み表を持つ係が 2026-11-04 14時に採点。見つけたの数は 2026-11-03 が 5、2026-11-04 10時が 7。`docs/評価.md`)。採点した出力の版は 7ba4f4f で、書類どうしの突き合わせ(F32a)が入っている。見つけた 9 件のうち 1 件は、仕込みの欄の一部だけを指摘した部分一致である。2 件は見落としている
- 文の置き換えの漏れの率: 規則を作るときに見た見本の書類では 4.2% だが、初めて見る書類4件では辞書に足さないと 37.8%、人名・現場名を足しても 14.3%(足しても会社名は 24語中11語、許可番号は4語中3語が漏れる。2026-11-04 朝に commit 520ced6 で、作る側ではない担当が測った値で、そのあとの置き換えの直し(F31・F36)では測り直していない。`docs/mask-rate.md`)
- 本物の Claude の API で、置き換えた後の架空の書類を1回送り、名前が記号のまま根拠つきの候補が返ることを人が確かめた

## 限界
- 指摘の候補であり、抜けが無いことの保証や合否ではない
- 段取りと記載項目は国の直轄の土木工事の例(画面で和歌山県の例の7つの節に切り替えられる)。自治体・民間は発注者の仕様書・契約書で置き換える
- 取り込んだのは一部の条と資料だけ。施行規則は第14条の2 だけで、契約約款は入っていない。法令の改正は取得日(2026-11-02。施行規則は 2026-11-03)まで
- 文の置き換えの漏れは0にならず、初めて見る書類では多い。外へ出す前に必ず目で確かめる
