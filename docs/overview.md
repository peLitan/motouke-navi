# プロジェクト概要
経験、ノウハウがないからこそ一から調べてやらなければならない<br>多くの経験がない若手や元請けを請けたことがない建設業に届いてほしい。<br>道具を使うことで若手に任せられるものが増えて、若手の教育を効率化できる。<br><br>

最初の3文は作者の言葉です。作者は建設の現場で働く1年目で、作者のいる部署は、いま初めて元請けに取り組もうとしています。大会のあと最初に使うのは、その仕事で、作者と身近にいる経験のある人です(入札の前と受注したあと)。3文目は作者の考えで、測った結果ではありません。

- 誰の: 多くの経験がない若手と、元請けを請けたことがない建設業の確認の仕事
- どんな場面で: 「この金額なら特定建設業の許可が要るか」「施工体制台帳は要るか、写しは出すのか」「監理技術者か主任技術者か、専任か」を、そのたびに建設業法・施行令・入契法と国交省の資料を引いて確かめている。受注のあとは、共通仕様書のどの条で、いつ・何を・誰に出すのかを、着手から引き渡しまで追う
- 何を: 入札前の確認・施工体制台帳の要否・受注後の段取り(着手から完成・引き渡しまで)・書類の点検の候補を、法令と国の仕様書の原文の抜き書きつきで出す
- どう: 使う前は法令と発注者の仕様書を自分で引いて確かめる必要があった元請けの確認を、使うと工事の条件を入れるだけで、読むべき原文の抜き書きつきの候補として見られます

元請けとしての決まりは建設業法などの法令と発注者の仕様書に分かれています。手がかりになる国の作成例は、国の直轄工事のものだけです。

作品名: Motouke Navi

テーマ: #2「本来、誰にでも届くべきものを。」 — 決まりが法令と仕様書に分かれていて読み解くのが難しい確認の手がかりを、元請けを請けたことがない建設業にも届けます

## 一言で
工事の条件を入れると、入札前の確認・施工体制台帳が要るか・受注後の段取りを、法令と国の仕様書の原文の抜き書きつきで出し、施工体制台帳と施工計画書の目次の抜けの候補も出す、ブラウザで開くだけの道具です。

## 誰の、どんな困りごとか
- 多くの経験がない若手と、元請けを請けたことがない建設業
- 国の直轄の一般土木工事では、D等級に登録した 9,734 社のうち、2016 年以降に単体の元請けで受注したのは 723 社です(国土交通省「中小建設業への普及促進方策について」p.2。北海道と沖縄を除く)。この数を、国の直轄の工事を元請けで受けた経験を社内で積む機会は限られている、と読みました(残る会社が県や市町村の工事で元請けをしている可能性は、この資料からは分かりません)
- 「この金額なら特定建設業の許可が要るか」「施工体制台帳は要るか、写しは出すのか」「監理技術者か主任技術者か、専任か」を、そのたびに建設業法・施行令・入契法と国交省の資料を引いて確かめている
- 受注後は、共通仕様書のどの条で、いつ・何を・誰に出すのかを、着手から完成・引き渡しまで追う必要がある
- 台帳や施工計画書の抜けは、監督職員に言われて初めて気づくことがある

## このツールがすること
1. 入札前の確認と台帳の要否: 公共・民間、請負代金、下請けの総額、許可の種類などから、受注したら要るものを、根拠の条(法令名・条・項)と原文の抜き書きつきで出す
2. 受注後の段取り: 工種を選ぶと表と出典が切り替わる(既定は土木)。国の直轄の例として、着手まで・施工中・完成・引き渡しの段に分け、土木工事共通仕様書(案)令和8年3月の該当箇所と抜き書きつきで一覧にする
3. 施工体制台帳の点検: 貼った台帳(または国交省の作成例の様式の Excel)から、空の欄・技術者の種類・特定建設業・専任の要否の食い違いの候補を出す
4. 施工計画書の目次の点検: 共通仕様書 1-1-1-6 の記載事項と比べ、見当たらない項目を候補に出す
5. 書類の突き合わせ: 施工体系図や施工計画書の目次も貼ると、下請負人の一覧・技術者の氏名・発注者の名前を台帳と比べ、片方にしか無い下請負人や氏名の違いを候補に出す。同じ会社か決められないときと発注者の名前の違いは「判断できない」に回す
6. 文の置き換え: 外の AI に貼る前に、人名・会社名・住所・電話などを記号に置き換え、戻ってきた文を元に戻す。置き換えた後のファイルだけを Claude の API に送って点検する手元のプログラムと、Claude Code が生のファイルを読む操作の多くを止める設定も付ける(止めきれない操作があり、README に挙げる)。施設名の語尾の表は建設のほかに、例として医療の表がある(医療の書類での漏れの率は測っていない)
7. Claude Code のプラグイン: 生のファイルの読み込みを止める hook、置き換えた後の中身だけを返す MCP の道具、取得した条に照らして書類を点検する Skill、その候補を崩しにかかる反証の係をまとめた。プラグインのあり・なしを比べる評価のケース2件(仕込み10件)と採点のスクリプトも付けた(2026-11-03 に12回走らせた。見落としは あり 5/30(すべて止まった1回)・なし 0/30 で、止まった1回のほかはどちらも0で、条番号と抜き書きが原文にある割合はありの方が高かったが、数え方がプラグインの側に有利で回数も各3回だけなので言い切らない。docs/評価.md の 5)。架空の書類1件で、プラグインを読み込ませて raw/ の Read が止まること・Skill と反証の係が呼ばれることを1回確かめた(置き換えの漏れ・置き換えすぎ、許可の確認が出ることも分かった。README の限界)

8. 参考の積算額: Skill `estimate` で Claude が数量の表の行を施工パッケージに当て、両方の抜き書きを付ける。機械が抜き書きと単位を照らし、通った行だけを、標準単価を公共工事設計労務単価で補正して積み、国交省の運用の式で共通仮設費・現場管理費・一般管理費等を足す。当てるのは Claude、照合と計算はプログラムで、AI は計算に使わない。画面にはまだ出ない

## 大事にしたこと
- 根拠を原文で示す: 規則表の行ごとに原文の抜き書きを持ち、機械で原文と照らす。合わない行は使わない。金額の境目もコードに書かず、抜き書きの文から読む
- 推測で埋めない: 入力から決められないことは「判断できない」と出す。結論は候補で、最後の判断は人がする
- 外へ出さない: 画面は外部と通信せず、入れた内容を保存しない。Claude に送るのは、置き換えた後の中身を利用者が確かめて「送る」と打ったときだけ

## Claude の使い方
作品の中では、Claude と機械が次の4つのように役を分けています。

1. Claude が Skill `spec-to-rules` で発注者の仕様書の文を読んで行にし、`plugin/skills/spec-to-rules/scripts/check-rows.mjs` が抜き書きを原文の節と照らして合わない行を外します(行の意味は人が確かめます)。
2. `read_masked`(`plugin/mcp/masked-files.mjs`)は、置き換えのたびに架空の語(decoy。`plugin/src/mask/decoy.mjs`)を混ぜて見落としを測り、結果を返事に乗せます(漏れの目安で保証ではなく、混ぜた語は置き換えた中身には入りません)。
3. 道具を `read_masked` と `check_articles` に絞った `refuter`(`plugin/agents/refuter.md`)が、点検の候補を1件ずつ崩しにかかります。
4. 公式の `claude plugin eval`(`plugin/evals/E1-trace-masked/`)で、架空の書類で調べた元の名前8つが trace に出ないことを確かめました(古い組(検査9つ)の値で、プラグインあり 8/8・なし 0/8、各3回。2026-11-05。答えの語の組と手順の印を足した新しい組は、版 17b7bc2(2026-11-07)で E1・E2 が不合格、E3・E4 が合格。E1・E2 のプラグインありの回で落ちたのは判定役の検査だけで、名前の漏れは測った範囲で 0。`docs/評価.md` の 7)。

**Claude Code で何ができたか**(コミットを数えた日時: 2026-11-06 23:06。反証以降の数は 2026-11-05 18:24 に数えた値)。コミットは 2026-11-02 20:48 から 2026-11-06 22:47 までに 205 件で(`git rev-list --count HEAD`。この数を書くコミットの前の数)、うち 202 件に Claude の共著の印があり、残る 3 件は別の担当が走らせた記録を足したものです。反証は、第3弾までの `docs/critic.md` の表にある4回(番号の無い 11/3 の1回と第1〜第3弾)で、指摘の 34 行のうち 33 行を「直した」とし、1 行(参考)はそのままにしました。第4弾の表は記録に残る直しの題から起こしたものなので、この数に入れていません。残っていることは同じ文書の各節に書いています。仕込みの点検の見つけた数は、11件のうち 5(11/3)→ 7(11/4 10時)→ 9(11/4 14時。うち1件は部分一致で、見落としが2件)と増え、公式の評価は古い組(検査9つ)で 7/8(11/4 の版)→ 8/8(11/5)になりました(`docs/評価.md` の 1・7)。どれも架空の書類での値で、回数も少なく、実際の書類での確かさを言い切るものではありません。

- 作り方: Claude Code が、1つずつの機能を短いセッションで作った。受け入れテストは人が承認したものを固定し、エージェントは直せない。原文の写しは reader、抜き書きの照合は checker、区切りの点検は critic という別の subagent に任せ、作る係の自己評価の甘さを補った(この3つは開始前に作った仕組みで、リポジトリの外にあり、審査の対象外。README の「Claude Code での作り方」)
- 作品の中: 置き換えた後の書類を Claude の API(`claude-opus-5-5`)に送り、点検の候補を「AI の候補」として、法令の決まりで判定した結果とは別の欄に出す

## 限界
- 公告の読み取り(Skill `bid-intake`)は、拾った値の候補を出すものです。機械が見るのは抜き書きの位置、数字と名前の形、決めた食い違いだけで、値の意味が原文に合っているかは見ません。拾いの正しさは、架空の公告5件(75欄のうち誤り1)と実在の公開の公告2件(30欄のうち外れ1。1つの欄で拾った全部の行で判定した数で、欄の最初の1行だけで判定すると外れ3)で測りました([docs/評価.md](評価.md) の8)。実在の公告では架空より外れの割合が高く、2件だけなので率としては読めません。元請けの施工実績を求める文は、語で探して結果の「確認が要る点」に抜き書きつきで出します(言い回しによっては漏れます)。入札に参加できるかの判断はしません
- 参考の積算額は Skill までで、画面には出ない。公表の積算内訳と比べると(docs/評価.md の9節)、間接費は地域の補正係数を入れないと 9〜30% 低く出る工事があり、数量からの直接工事費は公表の額の 0.5〜4.7% しか積めなかった(3件)。比べられた 12 種別は -11.4%〜-0.5% で、すべて公表より低い。機械が見るのは抜き書き・数量・単位の文字だけで、当て方が工事の中身に合っているかは見ません。機械・材料・市場単価の補正は空けてあり、会社の原価は含まない
- 指摘の候補であり、抜けが無いことの保証や合否ではない
- 建設業法施行令 第37条の技術検定の7種目のうち仕様書を読めた5種目は、土木・建築・電気工事・管工事・電気通信工事。読んだのは各仕様書の最初の章の一部の条で、作った段取りの行は順に 21・33・38・41・21 行、すべて `node scripts/check-quotes.mjs` を通った(2026-11-06)。残る2種目のうち、建設機械施工は専用の仕様書が無いので土木にまとめた。造園は公園緑地工事共通仕様書の表紙と目次の頁の注だけを読み、本文を読んでいないので5種目に数えていない
- 見ていない範囲: 建設業の許可の29業種のうちほかの業種の仕様書、改修の仕様書の本文(建築・電気工事・管工事で読んだのは新営の仕様書)、電気通信工事の共通費、機械の共通費のうち管工事の機械設備工事の別表に当たらないもの(建設機械施工に専用の基準など)。表の無い部分は「この工種の仕様書は見ていない」と出す
- 既定の段取りと記載項目は国の直轄の土木工事の例(画面で和歌山県の例の7つの節に切り替えられる)。自治体・民間は発注者の仕様書・契約書で置き換える
- 取り込んだのは一部の条と資料だけ(法令は29の条。`data/sources/index.json` の `kind` が `law` の行の数。2026-11-06 に数えた)。施行規則は第14条の2 だけで、契約約款は入っていない。法令の改正は取得日(2026-11-02。施行規則は 2026-11-03、労働安全衛生法の3つは 2026-11-05、施行令 第37条は 2026-11-06)まで
- 労働安全衛生法の候補(元方事業者の措置・統括安全衛生責任者と元方安全衛生管理者・計画の届出・作業主任者、下請けのときは安全衛生責任者と作業主任者)は結果の別のページに出す。取り込んだのは法・令・則の14の条(取得日 2026-11-05)だけで、機械等の設置の届出(法 第88条第1項)や店社安全衛生管理者は見ていない。法律の専門家の確認は受けていない。ブラウザでの見え方と、使う人にとっての分かりやすさは測っていない
- 文の置き換えの漏れは0にならず、初めて見る書類では多い。外へ出す前に必ず目で確かめる
