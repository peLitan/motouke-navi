# 仕様書から規則表を作る(Motouke Navi)

自治体の工事では、段取りや施工計画書に書く事項が、発注者ごとの仕様書で決まっています。
このスキルは、利用者が渡した仕様書の文から、Motouke Navi の規則表(`data/schedule.json` の段取りの行、`data/plan-items.json` の記載項目の行)と同じ形の行を作ります。
作った行は「候補」です。仕様書の読み方の判断や発注者の判断ではありません。最後は人が原文と照らして決めます。

## 守ること

- 根拠にしてよいのは、利用者が渡した仕様書の文だけ。覚えている国の共通仕様書や他の自治体の決まりで行を作らない。原文に無い行は作らない
- 行ごとに、原文から一字一句そのまま写した抜き書き(`quote`)を付ける。言い換えない・つなぎ合わせない・字体や全角半角を直さない(照合で許す違いは空白だけ)。ページをまたぐ文は、間のページ番号と欄外の見出しを入れずに写す(スクリプトが照らす前に原文から除く)
- 段取りの行の `quote` は決まりの文を写す(10字より短いと外れる)。「監督員に提出しなければならない。」のような文の尻尾だけを写さず、何を出すのかが分かるところから写す
- `when`・`what`・`to` は `quote` の言い換え。`quote` に無い期日・金額・相手を足さない(数字はスクリプトが確かめる。漢数字・全角の数字もそろえて、`when` の数字は `quote` の中、`what`・`to` の数字は同じ節の中に、同じ単位であるか)
- 原文から決められない欄は、値を `"判断できない"` にし、`undetermined` に理由を書く(例: 原文に時期の定めが無い、提出の相手が書いていない)。推測で埋めない
- 仕様書は公開資料なので置き換えは要らない。ただし `raw/` には置かない(`raw/` は工事の生の書類の置き場で、フックが止める)。例: `spec/` に置く
- 外へ送らない。スクリプトは手元で動く

## 手順

1. 利用者から仕様書の文のファイル(テキスト)を受け取る。PDF しか無いときは、文を写したテキストを頼む。どの発注者の、何年版の仕様書かを聞いて控える
2. 節の見出し(`1-1-1-6　施工計画書` の形。行の頭が番号、空白、題)を確かめる。見出しの形が違うときは、節の中を照らせず `section` も書けないので、行を作らずに利用者に伝えて止める(`section` の無い行はスクリプトが外し、画面の読み込みも拒む)
3. 施工計画書の記載事項の節があれば、列挙を機械で拾う:

   ```
   node <このスキルのフォルダ>/scripts/check-rows.mjs --list <節の番号> <仕様書のファイル>
   ```

   出た候補(`no`・`label`・`quote`)は原文の列挙をそのまま拾っただけ。記載事項でない列挙(下請負の要件など)が混じっていないか、原文を読んで確かめ、要らない行を除く。`no` は必ず数で書き、`quote` は列挙の1行の全体、`label` はそこから番号と末尾の括弧書きを除いた名前のまま(ほかの形の列挙、1行に収まらない項目は `--list` の出たとおりの行しか通らない)
4. 段取りの行を作る。受注者が「〜しなければならない」「〜提出する」「〜登録する」とされている文を探し、1つの決まりを1行にする
   - `phase`: `start`(着手まで)・`work`(施工中)・`completion`(完成・引き渡し)。段に分けるのはツールの整理で、原文は段で分けていないことが多い。決められなければ `"判断できない"`
   - `when`: いつ。原文に時期が無ければ `"判断できない"` にし、理由に「原文に時期の定めが無い」
   - `what`: 何をするか / `to`: 誰に(監督職員・発注者・登録機関など)
   - `section`・`title`: 節の番号と題 / `quote`: 根拠の文 / `note`: 人への補足(任意)
   - 金額や条件で行が要るかが変わるときは、`note` にその条件を書く(条件の欄はツールの側で人が足す)
5. 行をファイル(例 `tmp/行.json`。`raw/` の外)に `{ "source": { ... }, "rows": [ ... ] }` の形で保存し、照らす(`source` は手順1で聞いた発注者・題名・版。`--out` にそのまま写る):

   ```
   node <このスキルのフォルダ>/scripts/check-rows.mjs <仕様書のファイル> tmp/行.json --out tmp/残った行.json
   ```

   - 照らし方は作品の `scripts/check-quotes.mjs` と同じ(空白の違いだけ許す)。さらに、抜き書きが行の `section` の節の中にあるかを見る
   - 記載項目の行は、`quote` が節の列挙の1行の全体か、`label` がその名前か、`no` があり抜き書きの番号と合うかを見る
   - 段取りの行は、`phase` の値、`quote` が10字以上か、`what` があるか、`what` の「を」の前の語が1つでも `quote` にあるか(`quote` が「その写しを…」のように前を指すときは同じ文の前の部分まで見る)、`when` に抜き書きに無い数字が無いか、`what`・`to` に節に無い数字が無いかを見る(`what` は節の列挙をまとめることがあるので節まで見る)。数字は漢数字・全角も算用数字にそろえ、単位まで比べる(`500万円` があっても `500日` は通らない)。単位の無い数字と、単位の続かない漢数字は単位を比べない
   - 抜き書きで「土曜日、日曜日、祝日等を除き10日以内」のように数え方の条件が付く日数は、`when` にも「除き」を書く(無いと外れる)
   - 「判断できない」の欄に理由が無い行は外す
6. 外れた行は、理由を見て原文を読み直す。抜き書きの写し間違いなら原文から写し直して照らし直してよい。原文に根拠が無い行は直さずに外したままにする(根拠を探して作り変えない)
7. 利用者に見せる: 残った行の一覧、外した行と理由、「判断できない」の欄と理由、スクリプトの最後の行(行の数・残す・外す)をそのまま。照合で確かめたのは「抜き書きが原文のその節にあること」と上の形の点だけで、行の中身(いつ・誰に)が原文の意味に合っているかは機械では確かめていないことを書く

## 行の形

```json
{ "source": { "publisher": "〇〇県", "title": "土木工事共通仕様書", "edition": "令和7年4月", "url": "https://example.com/spec.pdf", "fetchedAt": "2026-01-01" },
  "rows": [
  { "kind": "plan-item", "section": "1-1-1-6", "no": 1, "label": "工事概要", "quote": "（1）工事概要" },
  { "kind": "schedule", "id": "start-plan", "phase": "start",
    "when": "工事着手前(または施工方法が確定した時期)",
    "what": "施工計画書を提出する", "to": "監督職員",
    "section": "1-1-1-6", "title": "施工計画書",
    "quote": "受注者は、工事着手前または施工方法が確定した時期に工事目的物を完成するために必要な手順や工法等についての施工計画書を監督職員に提出しなければならない。" },
  { "kind": "schedule", "id": "done-drawing", "phase": "completion",
    "when": "判断できない", "what": "工事完成図を作成する", "to": "判断できない",
    "undetermined": { "when": "原文に時期の定めが無い(設計図書に従う)", "to": "原文に提出の相手が書いていない" },
    "section": "1-1-1-23", "title": "工事完成図",
    "quote": "受注者は、設計図書に従って工事完成図を作成しなければならない。" }
] }
```

## このスキルでできないこと

- 行の中身が原文の意味に合っているかの判断(機械で確かめるのは抜き書きの位置と、数字・番号・名前の形だけ)
- 仕様書が最新か、特記仕様書で変えられていないか
- 画像の PDF の文字起こし
- 作った行を作品の規則表(`data/`)へ入れること。残った行のファイルは、人が画面の「段取りの表を読み込む」で開く(`source` の発注者・題名・版が無いファイルは画面が拒む)
